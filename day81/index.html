05

跟著做：每一步都有預期與失敗訊號

1

分層登錄五個唯讀觀察

輸入：逐列擷取 UI版本、Kernel build、服務頁、資料新鮮度、時區。

預期：形成五列互不推導的環境卡。

證據：每列保留模擬值、來源、09:00～09:04 時間與判讀。

失敗：合併 UI 與 Kernel 版本或漏掉來源時間即失敗。

2

計算測試序號的新鮮度

輸入：比較最後樣本 08:59 與觀察時間 09:03。

預期：得到 4 分鐘延遲，並註明同時區前提。

證據：保存 09:03−08:59=4 分算式及測試序號。

失敗：用 09:04 時區列替代觀察時間或算成5分鐘即不通過。

3

判讀服務頁角色不可見

輸入：使用「角色不可見／存取結果／UNKNOWN」。

預期：只記角色限制與待查 owner，不推論服務停止或不存在。

證據：UNKNOWN 清單含角色、觀察時間與需補證據。

失敗：以不可見宣稱服務異常，或猜測後端入口即失敗。

4

審核環境卡的禁止推論

輸入：對照 UI 7.x、K-sim-42、UTC+8 與五列來源。

預期：所有值明示虛構；沒有相容、Shell 方法或正式欄位宣稱。

證據：交付逐列列出能證明／不能證明。

失敗：出現未受控正式入口、命令或跨層相容結論即退件。

停止條件：環境、角色、版本、影響範圍、回復方式或核准任一項不清楚，就停在觀察與設計。

10

本課專屬排錯

環境卡把 UI 7.x 與 K-sim-42 合成同一個「系統版本」，或五列中缺少來源／觀察時間。

最小檢查：逐列核對 UI 版本、Kernel build、服務頁、資料新鮮度、時區是否各自保留模擬值、證據來源及 09:00～09:04 的觀察時間；確認沒有由 UI 推導 Kernel、資料庫或相容性。

預期：五個觀察項彼此獨立：UI 7.x 僅代表 UI，K-sim-42 僅代表 Kernel；每列都有來源、時間與可證明／不可證明的判讀。

修正：將合併的版本列拆回 UI 與 Kernel 兩列，依 fixture 補回各列原始來源與時間；缺證據的欄位標 UNKNOWN，不以其他層版本代填。

停止／升級：若無法指出某值的唯讀來源與觀察時間，或需要使用未受控入口、Shell、正式環境變更才能補證，該列維持 UNKNOWN 並停止延伸結論。

資料新鮮度被算成 5 分鐘，或拿 09:04 的時區觀察時間當作樣本比較終點。

最小檢查：確認被比較的是同一測試序號的最後樣本 08:59 與資料新鮮度觀察時間 09:03，並確認兩者採相同時區；09:04 只屬於時區列。

預期：證據中明列 09:03−08:59=4 分鐘，附測試序號與同時區前提。

修正：把計算終點改回 09:03，保留原始時間戳與算式；若時區尚未對齊，先將結果標為待確認，不自行換算未知時區。

停止／升級：測試序號不一致、任一時間戳來源不明或時區無法確認時，不得宣稱 4 分鐘延遲或資料正常。

因服務頁顯示「角色不可見」，報告便寫成服務停止、不存在或後端故障。

最小檢查：回看存取結果是否只有「角色不可見」，並檢查 UNKNOWN 清單是否記錄角色、09:02 觀察時間、待補證據及查證 owner。

預期：結論僅為可見性受角色限制、服務狀態 UNKNOWN；不猜測服務狀態、入口或部署方式。

修正：撤回故障或不存在的判定，改寫為 UNKNOWN，建立由受控 owner 確認角色、授權或部署差異的查證項。

停止／升級：未取得適用部署的受控證據前，不嘗試繞過權限、不猜後端入口，也不以不可見作為重啟或設定變更依據。
