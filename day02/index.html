LESSON 02 · DATA JOURNEY

資料如何進入
N-Cloud

一筆紀錄不會自己出現在 Dashboard。這一課要沿著資料走一次，理解每個階段負責什麼，以及資料在哪裡可能中斷。

本課目標
  1. 說出資料旅程的六個階段
  2. 分辨接收、解析與儲存的工作
  3. 依症狀判斷可能的中斷位置
建議時間：約 45–55 分鐘

本課章節

01 完整旅程 02 六個階段 03 為何正規化 04 常見斷點 05 排序實作 06 診斷實作 07 學習紀錄

01

Dashboard 是終點，不是起點

當你在畫面上看到一張趨勢圖，背後其實已經完成傳送、接收、整理、保存與查詢。任何一站出問題，都可能讓畫面看起來「沒有資料」。

今天的問題
「防火牆明明有產生事件，為什麼在 N-Cloud 搜尋不到？」

不要立刻怪搜尋畫面。先沿著資料旅程逐站確認，才能知道資料根本沒送出、送到了但沒解析，還是已經存在卻查錯時間。

核心觀念

「設備有資料」不等於「平台可搜尋」。中間每一站都要成功，資料才會變成可用證據。

02

六個階段，各有不同責任

把每一站的輸入、工作與輸出分開，排錯時才不會只會反覆按搜尋。

01

設備／服務

產生原始資料

事件、通聯、設備狀態或服務量測結果。先確認來源本身真的有資料。
02

網路傳輸

把資料送到正確目的地

檢查目的位址、Port、協定與路徑；設定正確不代表網路一定可達。
03

Receiver／Collector

接住不同來源的資料

接收端先確認「有沒有收到」，不等於已理解內容或可供搜尋。
04

Parser／正規化

把原始文字變成共同欄位

辨識時間、來源、目的、動作、結果等欄位，讓不同廠牌資料可比較。
05

Storage／Index

保存並建立可搜尋結構

索引讓查詢更快；保存時間則決定多久以前的資料還找得到。
06

Search／Dashboard／Alert

把資料變成問題的答案

搜尋找證據、Dashboard 看趨勢、規則與告警提醒需要行動的狀況。

03

為什麼不能直接只看原始文字？

不同設備可能用不同名稱表達相同概念。正規化的目的，是讓它們可以用同一套方式查詢。

原始紀錄 Atime=14:03 src=192.0.2.8 dst=203.0.113.20 action=deny 原始紀錄 Bevent_at=14:03 client=192.0.2.8 server=203.0.113.20 result=blocked
↓ 正規化
時間 14:03來源 IP 192.0.2.8目的 IP 203.0.113.20動作 阻擋

只有接收到

知道資料進來了，但欄位可能仍是一整段文字，跨設備搜尋很困難。

完成正規化

可用共同欄位搜尋、聚合與比較，也比較適合製作 Dashboard 和告警。

04

從症狀反推可能的斷點

症狀不是答案，但能幫你決定第一個檢查點。

看到的症狀優先檢查接著確認
接收端完全沒有資料來源設定與網路傳輸目的位址、Port、協定、路徑
有原始資料，但欄位都混在一起解析與正規化格式是否被辨識、欄位對應是否正確
今天找得到，較早資料找不到保存與索引保留期限、時間條件、索引狀態
搜尋有資料，Dashboard 卻沒有圖表條件時間範圍、篩選條件、指標與維度

真正環境的元件名稱與部署方式可能不同；這裡先學穩定的排錯邏輯，之後再對應實際 N-Cloud 版本。
