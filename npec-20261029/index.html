Q01N-Cloud 升級Firmware 7.0.027＋指定 KernelG3 變更

完整題目

先確認 N-Cloud Appliance 配備需求，再由題目 URL 下載 Image 並升級。Image：https://www.npartner.com/download/firmware/ncloud-7.0.027.img；升級後 Firmware 必須為 7.0.027，Kernel 必須為 3.10.0-1160.119.1.el7.x86_64。
證據層級：URL 與兩個目標版本是題目明示；最低 CPU／RAM／Disk、checksum、精確升級選單與升級順序沒有公開證據，必須依考場受控文件或實機預檢。

候選位置

系統管理 → 系統資訊／系統狀態（讀目前版本與資源）→ 系統升級／韌體升級（實際子選單名稱待 7.x 實機核對）。

設定表

項目設定／判定
Imagencloud-7.0.027.img
目標 Firmware7.0.027
目標 Kernel3.10.0-1160.119.1.el7.x86_64
實作機192.168.11.104
最低配備／雜湊題目未給；不得自行杜撰

逐步設定

  1. 在系統資訊記錄現有 Firmware、Kernel、CPU、RAM、系統碟／資料碟空間、節點角色與服務狀態。
  2. 依當期受控說明核對 7.0.027 的最低配備、來源版本、單節點／HA 升級順序及回復方式；任一 UNKNOWN 不直接猜。
  3. 先匯出設定或建立考場允許的回復點，寫下「預檢失敗、空間不足、套件驗證失敗」等停止條件。
  4. 從題目 URL 下載 Image，核對檔名與下載完整；若官方提供 checksum／簽章，再核對後才上傳。
  5. 進入實機確認過的升級入口，上傳 Image，先閱讀產品預檢；不可略過錯誤強行更新。
  6. 在核准時間執行，過程中不重複送出、不斷電、不強制重啟。
  7. 系統重新啟動後登入，分別讀回 Firmware 與 Kernel；兩者都要符合題目。
  8. 再驗證 Web UI、事件接收、Flow/SNMP/PM、查詢與排程服務，不能只看版本畫面。

驗收

  • Firmware＝7.0.027。
  • Kernel＝3.10.0-1160.119.1.el7.x86_64。
  • 至少一個已知來源能接收並查詢。
  • 升級前後設定物件沒有非預期遺失。

常見錯誤

  • 只核對 Firmware，漏掉 Kernel。
  • 把「可下載」當成已驗 checksum。
  • 未確認硬體空間與回復方式就升級。
  • 升級後未測資料鏈。
Q02Windows AD／DHCP／DNS／IIS 與 NXLogFacility 分流＋UDP 514接入設定

完整題目

針對 Windows Server AD／DHCP／DNS／IIS 建立設備，設定不同 facility（19／20／22），在 Windows Server 安裝 NXLog；參考 N-Partner 官網範例完成設定，將事件送往 N-Cloud 192.168.11.109 的 Syslog UDP 514。
重要缺口：題目列四種來源，但只列三個 Facility。19＝local3、20＝local4、22＝local6；IIS 的第四個值或四者對應順序，必須以原 PDF 圖面／考場補充確認，不能自行編成唯一答案。

候選位置

設備管理 → 設備資產樹狀圖／設備列表 → 新增設備；Windows 端為 NXLog 安裝目錄下的 conf\nxlog.conf（實際目錄與版本待確認）。

設定表

項目設定
目的端192.168.11.109:514/UDP（不是 192.168.11.104）
Facility19/local3、20/local4、22/local6；第四來源對應待確認
AD常見 input：im_msvistalog；Query 依事件通道
DHCP／DNS可能是 Event Log 或文字 audit/debug log；先看實際來源
IIS常見 W3C 檔案：C:\inetpub\logs\LogFiles\...

NXLog 設定骨架

<Extension syslog>
    Module xm_syslog
</Extension>

<Input ad_event>
    Module im_msvistalog
    # Query／QueryXML 依實際 AD 事件通道設定
</Input>

<Output ad_out>
    Module om_udp
    Host 192.168.11.109
    Port 514
    Exec $SyslogFacilityValue = 19; to_syslog_bsd();
</Output>

<Route ad_route>
    Path ad_event => ad_out
</Route>

# DHCP、DNS、IIS 各自建立 input/output/route；
# 不要讓四種資料共用同一 Facility。語法需依考場 NXLog 版本驗證。

逐步設定

  1. 先確認四個角色是在同一 Windows 主機還是不同主機；N-Cloud 的來源 IP 應填 Windows 真實來源，不是接收端 192.168.11.109。
  2. 在 N-Cloud 分別建立 AD、DHCP、DNS、IIS 邏輯設備；資料類型選 Syslog、傳輸 UDP/514。
  3. 依題目圖或考場說明把 19／20／22 對到正確來源；IIS 值未明示時保持待確認。
  4. Windows 安裝 NXLog，確認服務帳號有權讀 Security／Directory Service、DHCP、DNS、IIS 日誌。
  5. AD 建立 EventLog input；DHCP／DNS 先確認是 Event Channel 還是檔案；IIS 先確認 Site ID 與 W3C 路徑。
  6. 四種來源各自建立 Route 與 Output；Host 192.168.11.109、Port 514、UDP，並設定各自 Facility。
  7. 執行 NXLog 語法檢查，重啟服務，查看 NXLog 自身 log 是否有開檔、權限、連線錯誤。
  8. 四個來源各產生一筆可識別事件，在 N-Cloud 依來源、Facility、時間與內容回查。
  9. 必要時擷取 UDP/514 封包並解讀 PRI；看到 Port 514 不等於 Facility 正確。

驗收

  • AD／DHCP／DNS／IIS 四類都查得到。
  • 19／20／22 對應經題目或實機確認。
  • 原始事件與 N-Cloud 可用時間、來源、內容配對。
  • NXLog 重啟後仍持續送資料。

常見錯誤

  • 把 192.168.11.109 當 Windows 來源 IP。
  • 四個 input 全送成同一 Facility。
  • 把 IIS W3C 檔當 Windows Event Log。
  • 擅自指定 IIS 的未明示 Facility。
Q03SSL-VPN 下班登入監控與 RAW Relay18:00～08:00；一筆觸發告警＋轉發

完整題目

建立 SSL-VPN 登入成功與失敗監控。監控時間每日 18:00 至隔日 08:00，一筆即達門檻；告警內容要顯示帳號；符合條件的原始日誌以 Syslog UDP 514 轉發到 192.168.11.109。
先查資料：「來源使用者」只是常見候選；必須先從真實 VPN 成功／失敗事件確認帳號欄位、事件類別與 RAW DATA。

報表 → 分時監控報表 → 訂製分時監控報表；Relay 候選位置：編輯該統計組 → Syslog relay。

設定表

欄位設定
事件SSL-VPN 登入成功 OR 登入失敗；不含登出
時段18:00～隔日 08:00
門檻一筆即成立；若 UI 為 ≥，填 1
詳細欄位實際承載 VPN 帳號的欄位
Relay192.168.11.109:514/UDP，內容為 RAW DATA

逐步設定

  1. 找一筆成功與一筆失敗 VPN 事件，記下資料來源、結果、帳號與原文。
  2. 新增訂製分時監控，限制到正確 VPN 設備／資料來源。
  3. 成功與失敗用 OR，避免加入登出或一般管理登入。
  4. 設定跨午夜 18:00～08:00；儲存後重開確認沒有被反轉成白天。
  5. 統計採 Hit Count／累計，一筆即觸發；實際窗口與連續次數若必填，採能實現單筆觸發的最小值。
  6. 告警詳細欄位加入真實帳號欄位。
  7. 在同一統計組開啟 Syslog relay：192.168.11.109、514、UDP、原始日誌。
  8. 先儲存統計組，再儲存整份報表並啟用。
  9. 在 LAB 下班時段各產生成功與失敗一筆，核對告警帳號與接收端原文。

驗收

  • 18:00～08:00 成功／失敗均命中。
  • 08:00～18:00 不命中。
  • 告警有實際帳號。
  • 109 收到對應 UDP 514 RAW DATA。

常見錯誤

  • 只收成功或只收失敗。
  • 把白天設為有效時段。
  • 來源 IP 冒充帳號。
  • 收到統計摘要而不是原始日誌。
Q04Cisco Firepower 自定義資料格式Raw Log 正規化＋Facility 19Parser

完整題目

使用題目提供的 Raw Log（https://reurl.cc/aLpLOD）建立 Cisco Firepower 自定義資料格式並正規化，再以 Facility 19 建立對應設備，使事件可正確解析。
已驗證附件：短網址指向 no6_raw.log，內容為一行「月日時間＋逗號分隔 Tag: Value」。原文沒有年份、時區、Severity；不可假裝原文有這些值。

設備管理 → 自定義資料格式；完成後到設備管理新增 Cisco Firepower 設備並綁定格式。

樣本關鍵值

欄位預期
Src/Dst192.168.11.60 → 34.35.36.37
Port/Protocol55792 → 443；TCP
Action/ApplicationAllow；HTTPS
BytesInitiator 663；Responder 798（數值）
UserNo Authentication Required
URLhttps://www.npartner.com
設備 Facility19／local3

逐步設定

  1. 下載並保留原始樣本，不先修改空白、逗號或冒號。
  2. 新增自定義資料格式，名稱填「Cisco Firepower」。
  3. 先抽出前綴時間 Apr 20 03:20:10；補年／時區策略依產品設定明示，不硬寫固定年份。
  4. 主分隔為逗號＋空白；每個欄位只用第一個 : 分開 Key 與 Value，避免切壞 https://。

  6. IP 設 IP 型別；Port 與 Bytes 設數值；其餘先以字串保存；完整 RAW DATA 必須保留。
  7. 用原始樣本測試，再加入值含空白、URL 冒號、缺值、未知 Tag、欄位換序等反例。
  8. Parser 通過後建立 Cisco Firepower 設備，Facility 19；來源設備 IP 依考場實際值，不可拿樣本 SrcIP 代替。
  9. 綁定格式並送測試事件，到事件查詢核對欄位與原文。

驗收

  • IP、Port、TCP、Allow、HTTPS 皆正確。
  • 663／798 為數值。
  • User 含空白未被錯切。
  • URL 完整保留。
  • 事件歸到 Facility 19 設備。

常見錯誤

  • 用所有冒號 split，URL 被截斷。
  • SrcIP 當設備來源 IP。
  • 自行補固定年份或時區。
  • 只測唯一正常樣本。
Q05匯入台南市中小學 Public IP 網段學校名稱解析＋Flow批次資料

完整題目

使用題目 Excel（https://reurl.cc/D4a2Wj）匯入台南市各中小學 IP 網段，以學校名稱建立名稱解析，並對 Public IP 網段啟用 Flow 分析。
附件實查：共 281 筆資料，280 筆可由 IPv4 parser 讀取；至少有 1 筆明確無效 CIDR、2 筆非 canonical 網段、8 組重複網段。不可未檢查就整份匯入。

系統管理 → IP 名稱解析 → IP 名稱解析列表 → 匯入（實際按鈕與模板欄位待版本確認）。

重要資料品質

案例處理
210.71.213,0/24無效 CIDR；疑似 .0/24，但需資料 owner 確認
121.121.121.255/24非 canonical；不可靜默改成 .0/24
120.115.26.1/23非 canonical；不可靜默改成 .0/23
重複網段總校／分校共用；依產品別名或 owner 決策
IPv6題目未要求，不直接混入 IPv4 匯入

逐步設定

  1. 先從 N-Cloud 下載當期匯入模板；來源 xlsx 欄名不一定可直接匯入。
  2. 建立工作副本，檢查空值、CIDR、重複、中文編碼與上述三筆異常。
  3. 釐清同網段多校名的政策：主要名稱、合併名稱或產品別名；不要建立兩個互相覆寫的 active 名稱。
  4. 轉成產品模板：名稱＝學校名稱、網段＝核准的 IPv4 CIDR、Flow 分析＝啟用。
  5. 先匯入 3～5 筆無衝突資料，確認中文、CIDR 與 Flow 狀態。
  6. 刪除或保留小批依考場流程決定，再分批匯入完整核准清單；記錄成功／失敗列。
  7. 失敗列單獨修正與重試，不重複匯入整批。
  8. 抽查 /23、/24、/25、/26 與重複網段處理結果。
  9. 以任一網段內 IP 查詢，確認顯示正確校名且原 IP 仍保留。

驗收

  • 成功筆數與核准清理後來源一致。
  • 無效 CIDR 未被默默接受。
  • 所有匯入 IPv4 網段啟用 Flow。
  • 查詢可顯示正確校名。

常見錯誤

  • 原始 xlsx 未檢查就全量匯入。
  • 靜默修正三筆異常。
  • 同網段建立兩個衝突名稱。
  • 只做名稱解析，漏勾 Flow。
Q06NAS 檔案讀取 Top N 日報帳號＋路徑＋檔案大小Top N

完整題目

針對 NAS 稽核，調閱離職員工在離職前 3 個月是否盜取機密；製作 Top N「公司檔案伺服器讀取資料排名」，內容包含來源使用者帳號、檔案路徑，以帳號抓取檔案大小排名，設為每日報表。
依賴：題目環境的 NAS 為 192.168.11.22。離職日與員工帳號未提供，所以只能完成每日報表；三個月個案調閱要等實際日期與帳號。

報表 → Top N → Top N 報表

設定表

欄位設定
名稱公司檔案伺服器讀取資料排名
設備Synology NAS 192.168.11.22
事件實際標準化的檔案讀取／Read
第一層來源使用者帳號
明細／第二層檔案路徑
統計值檔案大小／Byte(s)，不是 Hit Count
排程每日報表

逐步設定

  1. 先查 NAS 真實讀取事件，確認帳號、路徑、Bytes、讀取動作各自欄位。
  2. 建立 Top N，製作依據選 Syslog；設備條件選 192.168.11.22。
  3. 若實機標準化為「稽核 → Windows 檔案分享 → 檔案讀取」且資料真的如此，使用它；否則依真實 NAS 欄位選 read/File。兩套不要疊成 AND。
  4. 主分組選來源使用者帳號，明細或第二層加入檔案路徑。
  5. 統計值選真正的檔案大小／Bytes，先抽樣確認不是空值或固定 0。
  6. 檢查加入路徑後是否把帳號拆成「帳號＋路徑」聯合分組；若是，確認介面仍可加總帳號總量。
  7. 名稱填「公司檔案伺服器讀取資料排名」，勾每日報表並儲存。
  8. 用已知大小的 LAB 檔案做讀取測試，核對帳號、路徑與 Bytes。
  9. 取得離職日與帳號後，另用絕對日期查離職日前 3 個月，不把每日排程當成三個月結果。

驗收

  • 每列有帳號與檔案路徑。
  • 排名為 Bytes，不是事件數。
  • 手工加總樣本可對上報表。
  • 每日排程重開仍存在。

常見錯誤

  • 使用舊題 NAS 192.168.11.100。
  • NAS IP 填進來源 IP 條件。
  • 動作＝允許當成讀取。
  • 每日資料冒充離職前三個月。

Q09外對內重要服務 Port 連線告警同一來源 3 分鐘 5 次Top N＋腳本

  1. 抽查 Syslog／Flow，確認一筆資料是否真的代表一次連線，並能取得來源、目的與目的 Port。
  2. 來源設 !Home；目的範圍依重要服務實際資產設定，題目未指定就不硬填整個 Home 或 DMZ。

  • 五 Port 設成 AND。
  • 使用來源 Port。
  • 來源 IP＋目的 Port 分組造成拆散。
  • 只建報表，沒有腳本或執行記錄。
